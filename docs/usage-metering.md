# Model usage and workspace allowances

Status: Implemented locally; final compatibility checks and release acceptance
are pending. Additive migration **0021** stores prices, allowances, attempts and
append-only model events without changing the older product-usage ledger.
No real workspace allowance, commercial plan or price has been configured.

Every outbound provider attempt belongs to an authorized actor, workspace and
fixed operation category. Durable conversations use the saved turn identifier;
other operations receive a new identifier. Nested calls preserve the parent
operation and cannot switch actor or workspace. Attribution contains no prompt,
uploaded values, generated content, credentials or model API keys.

A workspace allowance is explicitly assigned by an active operator. It includes
a declared time window, optional attempt and local concurrency limits, and an
optional currency, spending limit and per-attempt reservation. There are no
invented commercial tier prices. An expired allowance stops new work until an
operator changes it; it does not silently become unlimited. Workspaces without
an assigned allowance remain unlimited. Provider attempt retries each consume
their own allowance and receive a distinct record.

Reservations and their append-only events are serialized by workspace. A unique
attempt identifier prevents duplicate reservation or reconciliation. Dispatch is
a one-way transition: the same attempt must never be sent to the provider again.
Only a reservation known not to have been dispatched can be released without
provider evidence. A timeout, cancellation, interrupted process or malformed
provider response leaves unknown cost explicit and retains reserved exposure.
Local concurrency describes local requests, not a guarantee that a timed-out
provider has stopped its own computation.

Provider counters are bounded nonnegative integers; missing, malformed, negative,
boolean or implausibly large counts never become zero. A versioned immutable price
record declares rates for input, optional cached input and output, the currency
and an operator evidence reference. Decimal arithmetic calculates a cost from
reported tokens without rounding intermediate values. A missing cache breakdown
cannot be given an invented discount. Unknown rates, missing counts and currency
mismatches leave cost unavailable. Truncated or rejected text still retains any
valid usage reported by the provider.

The spending check uses known cost plus held exposure and the proposed reservation.
A reservation is a locally configured exposure amount, not a verified upper bound
on the provider's invoice. If later reported cost exceeds it, the complete cost is
recorded and subsequent work is blocked when the allowance is exhausted. Neither
token counts nor costs are clipped to make the budget appear respected. A provider
invoice is not generated by this feature.

Unknown financial exposure can be settled only by an explicit operator action
referencing an independent provider usage record or invoice record. The operator
attests to that evidence; Syntelio does not automatically verify an external bill.
The settlement event retains operator identity, exact amount, currency and evidence
reference. It does not invent missing token counts or replace the original provider
outcome. Repeated identical settlement is idempotent; conflicting evidence fails.

Owner summaries show known subtotals, held exposure, unknown attempts, token-count
coverage and allowance state. They do not present an incomplete subtotal as a
complete bill. Summaries require full workspace data access as well as ownership,
so operational counts cannot bypass a dataset access policy. Individual prompts
and user conversation histories are excluded. A configured metering path refuses
unattributed requests and refuses outbound calls when durable admission fails.

Acceptance requires concurrent reservation and retry fixtures, idempotent events,
provider failure/cancellation/truncation coverage, crash recovery, explicit unknown
usage, exact pricing, owner/operator/privacy checks, policy changes, rollback
preservation, and held exposure during storage outages. Commercial billing,
payment-driven entitlements and independent financial/security acceptance remain
outside this internal allowance implementation.

## API and operating boundaries

- `GET /workspaces/{id}/model-usage?days=30` returns owner-only aggregates for
  one to 366 days. Exact token and monetary values use strings; absent values
  remain null. The report window and current allowance window are separate.
- `POST /admin/model-prices` accepts an explicit immutable price ID, exact
  provider/model names, currency, decimal rates, evidence reference and effective
  time. Identical retries are safe; conflicting IDs/effective times are refused.
- `PUT /admin/workspaces/{id}/model-allowance` uses `expected_version` and an
  explicit window/limits. It does not install default commercial tiers.
- `GET /admin/workspaces/{id}/model-usage/pending` lists up to one hundred
  unresolved attempts with identifiers and operational metadata only.
- `POST /admin/workspaces/{id}/model-usage/recover` takes an explicit `older_than`
  cutoff at least fifteen minutes old. It safely releases undispatched reservations
  and marks dispatched attempts interrupted/unknown. It never retries them.
- `POST /admin/workspaces/{id}/model-usage/{attempt_id}/reconcile` requires
  an exact cost/currency plus `provider_usage_record` or `provider_invoice_record`
  and its independent reference. It does not manufacture missing token counts.

All administrator routes require an active staff administrator grant. Pending
inspection, recovery and reconciliation also require membership and full workspace
data access. Price/allowance configuration is an explicit control-plane action.
Operator writes retain append-only identifiers and audit records, never model text.

Admission runs in short database transactions with a two-second lock timeout and
a five-second statement timeout; no database lock spans a provider HTTP request.
An admission outage prevents dispatch. A settlement outage prevents publishing a
successful response, retains the durable dispatched reservation, and logs only a
fixed diagnostic code. The operator can later recover and reconcile it. The
ledger is not a transactional outbox for external providers: a process crash
between dispatch marking and the HTTP call conservatively retains unknown exposure.

Allowances are checked when reserving a provider attempt. An already reserved
attempt keeps that approved exposure; membership is checked again before dispatch.
Changing a limit within the same time window includes prior attempts and known
costs. A spending allowance cannot silently treat old unpriced attempts with no
reservation as free, or convert costs in another currency. It returns
`usage_unresolved` until independently reconciled, or an operator explicitly
assigns a separate future window. The old unknown records remain visible.

No historical provider usage is backfilled or inferred. A price becoming available
later does not silently rewrite earlier unknown attempts. Pricing is based on
provider-reported counters, not independent tokenization or a certified invoice.
Owner summaries do not expose per-user conversation histories. Existing arithmetic,
model routing, token budgets and provider configuration remain unchanged.
